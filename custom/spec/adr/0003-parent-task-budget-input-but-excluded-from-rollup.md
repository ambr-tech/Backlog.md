# 親タスクの見積/実績は入力可とするが Milestone ロールアップには含めない

`subtasks` を持つ親タスクと、持たないリーフタスクのいずれも `estimatedDays` / `actualDays` の入力を許可する。ただし Milestone の予算ロールアップは **リーフタスクのみ**を母数とし、親タスクの値は集計に含めない。これにより「分解前の概算見積を親に残しつつ、分解後はリーフに値を入れる」というワークフローを破綻なく回し、かつ親子の値が二重計上される事故を防ぐ。保存は柔軟・集計は厳密、という役割分離を意図する。

## Considered Options

- **(採用) 親は独立値、Milestone 集計はリーフのみ** — 親もリーフも自由に入力可能。集計関数側でリーフのみフィルタする。
- **親は自動集計（read-only でサブタスク合計）** — 親値の入力を UI レベルで禁止し、サブタスク合計を表示する。分解前の概算見積を残せず、分解前後で UI 挙動が不連続になる。
- **親は工数を持てない（コンテナ扱い）** — 入力時に「これは親タスクなので入力不可」のエラーを CLI / MCP / Web UI 全てで実装する必要があり、複雑度が高い。

## Consequences

- 親タスクの詳細ページでは、参考表示として「サブタスク合計 = X.Xd」を親自身の値と並べて表示し、乖離を視認できるようにする。
- ユーザーが意図せず親とサブタスクの両方に値を入れた場合でも、Milestone 集計が二重計上されることはない（リーフのみ集計のため）。代わりに親自身の値はマイルストーン集計には反映されないことを UI 上で明示する必要がある。
- `unestimatedTaskCount` / `doneWithoutActualCount` の母数もリーフタスクのみ。親タスクの未入力はカウントしない。
- 将来「親タスクの値を必ず合計から除外する」前提を反転する場合、すべての rollup 関数の集計対象を変更する必要があり、リバースコストは中程度。本 ADR で意図を明示することで後続の判断者が方針を誤らないようにする。
